Behavior-preserving refactor plan — 2026-10-29

This proposal was based on the working tree at `403b0ad`. Passes 0–3 have now been implemented locally; see `refactor-contracts.md` and `refactor-parity.md` for their scope and validation. The remaining passes are proposals. Keep the Astro public site and the separately deployed Node perks portal as they are, preserve public URLs and contracts, and make each change independently reviewable and revertible.

The existing conventions are suitable: Astro page components, TypeScript data/helpers, small ESM scripts, and Node's built-in test runner. Modernization should reduce coupling within those conventions. It does not require a new framework or dependency upgrade.

**Baseline and prerequisites**

The working tree was clean before this plan. Inspection ran the existing suites directly, without build hooks:

- `node --test tests/*.test.mjs`: 49 passed.
- `node --test apps/perks-portal/tests/*.test.mjs`: 52 passed, one failed, one skipped. The failure is `preflight reads only its app project link and does not emit credentials`: this shell runs Node 26.12.1, while the release check requires `>=22.23.4 <23`. The optional real-Redis test was skipped because `REDIS_SERVER` was not configured.
- These results do not establish a green baseline on the supported runtime. Astro diagnostics, a full live-feed build, SEO/CSP checks, browser comparisons, and hosted redirect checks were not run during planning.

First use the repo's existing Node 22 requirement; do not relax the preflight to accommodate the inspection shell. Record a green supported-runtime baseline before implementation. Build hooks regenerate content dates and image variants, so review their diffs separately from refactor edits.

Before broad changes, create these small artifacts:

Include archived routes that must remain 404.
2. `docs/refactor-parity.md`: baseline commit, runtime, exact commands, fixture versions, representative browser states/viewports, observed skips, and per-pass results. Capture navigation at 880/881px, representative phone/desktop widths, keyboard focus, reduced motion, and back navigation.
3. Focused fixtures under the existing test directories: sanitized feed inputs and expected output, route/metadata/RSS/sitemap records, representative rendered markup, synthetic portal request/response cases, and a temporary Git-history fixture for content dates. Keep screenshots and private data out of committed fixtures; use ignored `.artifacts/` for local visual evidence.

Compare the same inputs before and after. Freeze feed responses, clocks, and synthetic identities at the test boundary. Normalize only known nondeterministic output such as asset hashes; retain URL, content, ordering, accessibility, and date assertions. Keep live-feed failures release-blocking. Do not introduce a production fixture fallback or change ingestion behavior to make tests pass.

**Validation and completion rules**

For each pass, state the behavior contract, files changed, structural benefit, and before/after evidence in the PR. Keep formatting-only changes separate from control-flow changes. Preserve existing imports via facades when moving modules. Preserve public component props, routes, query parameters, CLI commands, environment names/defaults, cookie/token formats, and persistence formats. Any necessary contract change becomes an explicit migration proposal before implementation.

Use `npm run validate:code` and the affected portal tests for fast checks. Before merging a public-site pass, run `npm run validate`; use `VERCEL=1 VERCEL_ENV=production npm run validate` when analytics/redirect/layout/security output is affected. A full build requires the live Substack feed; run baseline/candidate fixture comparisons separately so feed changes cannot disguise regressions. Rebuild with normal local analytics settings before browser preview. Check deployed redirect/proxy/header behavior on an approved preview when that layer is touched.

For portal passes, run `npm --prefix apps/perks-portal test` and the existing synthetic fixture-build test. Require `REDIS_SERVER` for storage changes rather than treating a skip as validation. A real portal build requires the ignored private catalog; its omission is a documented validation limit, not a reason to publish private data or add a public fallback.

Do not expand this into blanket test or tooling replacement. GitHub Actions currently runs code checks and portal tests; the Vercel status covers the live public build/SEO/CSP checks because Substack blocks GitHub runner IPs. Preserve those protections while adding focused fixture checks where useful.

**Separate migration tasks, if later requested**

- Astro, TypeScript, Node, npm, or dependency upgrades: separate compatibility, lockfile, runtime, and deployment validation. Using the already-required Node 22 locally is environment alignment, not a migration.
- Converting the portal to TypeScript, Astro SSR, another server framework, or merging deployments/workspaces: separate architecture proposal and release/rollback plan.
- Changing routes, redirects/statuses, cookies, invitation encoding, environment contracts, Redis schemas/keys, rate-limit storage, or entitlement identity: separate API/data migration with compatibility and rollback analysis.
- Introducing a CMS/content collection conversion, persisted feed cache, or different fail-open policy: separate content/availability decision. Changing what `dateModified` means is likewise separate from moving files.
- Introducing a new browser-test runner, CSS framework/layers, or shared cross-app design system: separate tooling/design decision. Existing browser tooling and focused checks can establish parity first.

Recommended first implementation tranche: baseline/contracts, confirmed dead-code removal, shared redirect rendering, and resource dispatch. Review the reduction in coupling before proceeding to stylesheet, content-history, feed, or portal work.
